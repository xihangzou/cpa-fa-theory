# Workflow 1 — JPGs to structured Markdown

Purpose: reproduce the conversion approach of `bookkeeping-text`, `bookkeeping-2-commercial`, and `bookkeeping-2-industrial`. Input is the designated page JPGs for one textbook. Output is the source-faithful structured Markdown for that textbook, ready for independent integration or card generation.

## Start prompt

> Run only the JPG-to-Markdown workflow in this folder. Source JPG folder: [absolute path or exact Drive link]. Textbook and edition: [title/version]. Scope: [physical page IDs or task IDs]. Output folder: [path]. Read the designated images, create and verify structured Markdown chunks, and assemble this textbook’s clean Markdown. Preserve the source’s meaning, conditions, examples, calculations, and terminology. Deliver source/page/task records and QA evidence, then stop at the Markdown handoff.

For an existing GitHub task, include its repository and issue ID. Read the live execution and conversion rules before operating. A folder name without an exact location is insufficient if multiple folders match.

## Process and fidelity rules

1. Preserve originals and register page images with stable source ID, filename, SHA-256, physical page number, printed label, and include/exclude decision. Use `page-001.jpg` numbering by physical PDF/source sequence; never assume printed-page offsets. Verify page identity, order, orientation, legibility, and completeness visually.
2. Divide processing into coherent section-sized tasks with expected images, optional explicit Processing images subset, chapter/section IDs, and output path. Retain all evidence needed to interpret a table or worked example. Required missing/illegible images block that task; continue independent complete tasks if useful.
3. Read only the designated processing images. OCR or text extraction can help if the task allows it; validate against the page images. Do not fill gaps from web content, prior chat, another folder, or general knowledge.
4. Write concise structured knowledge. Preserve definitions, distinctions, conditions, exceptions, timing, reasons, procedures, formulas, units, comparison tables, and useful numerical reasoning. Remove decoration and redundant prose. Preserve diagram-only information in text/tables, or retain an essential figure with its locator if verbalization would lose meaning. Do not generate Clozes at this stage.
5. Use chapter `#`, section `##`, topic `###`, subdivision `####`. Do not use bold in source Markdown. For accounting, preserve the debit/credit/amount table and relevant intermediate calculations. For another subject, preserve its equivalent structural details. Do not force accounting terminology onto it.
6. Review every processed page against its chunk, including sidebars and exceptions. Record uncertainty with `[UNRESOLVED: page, location, problem]` or `[要画像確認: ...]`; resolve before marking the chunk ready.
7. Assemble in explicit task order: remove chunk YAML and duplicated continuation chapter/section headings only. Do not summarize, paraphrase, deduplicate body text, or integrate topics from other textbooks. Fix source errors in the chunk and rerun review before reassembly.

## Local helper

Create a Python environment and install `requirements.txt`, then use:

```bash
python scripts/source_md.py init /path/to/source-project
python scripts/source_md.py ingest /path/to/source-project /path/to/page-jpgs --source-id BOOK1
# Complete edition, printed labels, exclusions, tasks and reviewed chunks.
python scripts/source_md.py check /path/to/source-project
python scripts/source_md.py assemble /path/to/source-project
```

The input directory must contain only `page-NNN.jpg` files. Copies preserve their bytes. A PDF may replace the JPG directory for optional upstream rendering; that requires Poppler (`pdftoppm`, `pdfinfo`), normally at 300 DPI. Export slides faithfully to PDF before using that utility; verify speaker notes/animations separately when in scope. The helper does not perform visual transcription.

## Project records

`sources.json` is generated by ingest. Complete its edition and printed-page fields and explain exclusions. Included pages must have exactly one processing owner. Source images and original PDF, when applicable, are checked against their hashes.

`tasks.json` is ordered by chapter and section. Example:

```json
[{"id":"SRC-001","chapter":"01","section":"01.1",
  "expected_pages":["BOOK1:022","BOOK1:023"],
  "processing_pages":["BOOK1:022","BOOK1:023"],
  "output":"chunks/SRC-001.md","status":"pass"}]
```

Omit processing_pages to process all expected pages. `pass` means the source-to-chunk review actually happened, not merely that a file exists. Each task covers one section; continuing chunks reuse its section ID. The chunk starts with:

```yaml
---
id: SRC-001
pages: "2-3"
pdf_pages: "22-23"
chapter: "01"
section: "01.1"
title: "Source section title"
---
```

Then write the chapter/section headings and structured body. The assembler checks task/chunk IDs, required source ownership, hashes, unresolved markers, and repeated heading consistency. Preserve precise page-to-topic locators in a separate QA/source map; the helper’s assembly.json supplies chunk-to-page mappings, not word-level source alignment.

## Deliver and stop

- Reviewed `chunks/*.md`, clean `merged/chapter-*.md`, and `merged/textbook.md`.
- `sources.json`, `tasks.json`, `merged/assembly.json`, and a concise source-fidelity QA report.
- Exact origin/edition and merged-file hash or pinned commit for the next workflow.

No integration map, ALP inventory, or Anki package is required here. The user can give this output independently to workflow 2 or directly to workflow 3.
